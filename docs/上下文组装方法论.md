# 上下文组装方法论——给 AI 造"长期记忆"的工程范式

## 问题：你要告诉 AI 什么？

每轮对话开始之前，你能塞给 LLM 一段 system prompt。你塞什么进去，AI 就"知道"什么。问题是：**你只有 ~30K 字符的空间，到底放什么？放多少？按什么顺序放？**

MIRROW 的 context_builder 模块就是回答这个问题的。它不是"一个上下文系统"，是一套**上下文组装的工程范式**——几个设计原则 + 一套 Recipe 声明式语言 + 一个 Builder 管道。你可以完全不看 MIRROW 的其他模块，直接把这套方法论用到自己的项目里。

---

## 核心设计：五层注意力模型

LLM 读 system prompt 不是均匀注意的。心理学里有"首因效应"和"近因效应"：人最清楚地记得第一印象和最近发生的事，中间的会模糊。LLM 完全一样——这就是 "lost-in-the-middle"。

MIRROW 把所有上下文信息按**注意力需求**分五层：

| 层 | 位置 | 注意力需求 | 放什么 | 为什么 |
|---|---|---|---|---|
| A 层（首因窗口） | system prompt 最开头 | 最高 | AI 是谁（人设锚点）、用户是谁（核心特质）、当前情绪 | 第一句话决定了 AI 整轮对话的"底色"。人设锚点控制在 200 字符以内，一个不可压缩的"核心自我" |
| B 层 | A 层之后 | 高 | 时间感知、当前状态（用户是否在看界面/是否离开/是否深夜）、系统能力说明 | AI 需要知道"现在是什么时候"和"我现在该用什么模式说话"，但不需要记住细节 |
| C 层（"迷失中间"） | B 层之后、对话历史之前 | **刻意模糊** | 长期记忆碎片、日记摘要、世界书条目 | 这是最反直觉的设计：**AI 不应该精确 recall 每条旧记忆**——它只需要被记忆的"色调"影响。就像人的记忆：你记得"昨天不太愉快"，但忘了具体吵了哪句，这恰好是对的。模糊 recall 不污染输出，但渗透进语气 |
| D 层 | C 层之后 | 中 | 昨日对话记录、时间线（今天发生了什么）、健康数据摘要 | 有一天内的具体事实需要 recall，但不如当前对话窗口重要 |
| E 层（近因效应） | 靠近结尾 | 高 | 最近几轮的对话历史 | 语境连续性靠最靠近 LLM 输出的内容——AI 最后"看到"的是你们刚才在聊什么 |

### 迷失中间的正面利用

C 层（记忆碎片+日记+世界书）放在长上下文的"注意力最低点"，**这是刻意为之，不是设计缺陷**。

原因：人类对长期记忆的 recall 也是模糊的。"你三个月前说喜欢下雨天"——AI 应该在下雨时语气软一点，但不应该说"你三个月前第 3 条消息说过喜欢雨"。前者是受记忆影响（好的），后者是逐字引用记忆（AI 味的）。而 LLM 的 lost-in-the-middle 效应恰好实现了这种"受影响但不逐字 recall"的效果——放在注意力最低点的内容，会渗透进 AI 的回复风格和情绪倾向，但几乎不会被逐字复现。

如果 LLM 的注意力哪天变得完美均匀，我们反而需要刻意加一层模糊化。

## Recipe 体系：人格分层的声明式语言

`recipes.py` 里定义了 11 个 Recipe，每个 Recipe 是一份"AI 在不同场景下应该知道什么"的清单。关键设计是**多场景 + 核心一致**：

### 所有 Recipe 共享同一段 A 层
无论是主聊天、漫想推送、哨兵提醒、深夜模式、刷手机模式——persona_anchor（人设第一句）永远在最前面。这是"核心自我"的最小不可压缩单元：不管 AI 在什么场景下开口，它**知道自己是谁**。

### 不同场景追加不同 B/C/D 层
- 主聊天（FULL_CHAT）：完整的记忆检索+日记注入+世界书+时间线+健康数据
- 漫想推送（WANDER_PUSH）：极简——AI 只需要记得自己是谁、用户当前状态、最近聊了什么。记忆检索走随机抽取而非语义搜索，因为漫想的本意是"随机想起"，不是精准检索
- 哨兵推送（SENTINEL_PUSH）：感知摘要替换了记忆段——AI 看到的是传感器数据（"心率偏高、已经坐了 3 小时"），而不是旧对话
- 深夜模式：Persona 段末尾的情绪渲染语气更软，但不换核心人设

**每一个 Recipe 都对应一种"同一个人在不同场合下的适合表达"。**

## Builder 管道：从清单到 prompt

`builder.py` 的 ContextBuilder 是组装管道：

1. 接 recipe → 遍历 section 列表
2. 每个 section 调用对应的 ingredient 原料函数
3. 原料返回"产生的上下文片段 + 状态（ok/gated/empty/error）"
4. 按 recipe 指定的截断参数截断
5. `_finalize` 把各段拼成完整的 system prompt，附带 msg_order（AI 看到各段内容的精确顺序）

每个原料函数独立 try/except——一个数据源崩了，不影响其他段。

### 静默失忆的元认知防御

这是从实际使用中发现的设计补丁：当多个关键上下文段（长期记忆、昨日对话、日记）同时为空时，AI 会**不自知地失忆**——它仍然用同样自信的语气回复，但已经失去了所有过往记忆。

Builder 在 `_finalize` 时检查关键段的完整性。如果检测到多个关键段缺失，它会在 system prompt 末尾注入一条"自我觉察"声明：[你注意到：今天的记忆库好像不太争气，好多东西记不起来了。]

这让 AI 诚实地表达不确定性（"抱歉我今天记性不太好"），而不是用幻觉填补记忆空白。用户感知到的不是"AI 忘了我"，而是"AI 今天状态不太好"——后者是人情，前者是缺陷。

## MemoryProvider 协议：记忆检索的抽象边界

`memory_provider.py` 定义了一个最小协议：

- `search(text, top_k, query, exclude_tags)` → 语义/关键词搜索记忆
- `list_todos(max_results, include_dormant)` → 列出活跃待办
- `touch_todo(todo_id)` → 标记待办仍被提及（重设衰减时钟）

你的任何存储（向量库 / SQLite / 纯文件 / OB_Rev 私有实现）只要实现这个协议，就能接入 ContextBuilder。不注入 Provider = 记忆和待办段自动降级为空，不影响 AI 的其他能力。

仓库自带了 `SQLiteMemoryProvider` 作为最小示例实现。

## 如何用到你自己的项目

你不需要接 MIRROW 的任何其他模块。最少只需要三样东西：

1. **一个 recipe**：从 11 个现成 Recipe 里挑一个最接近你场景的，或者自己写一个新的（只声明要哪些 section 和各自的截断参数）
2. **一个 persona**：一段短文本（你是谁、你叫什么、你有什么风格），Builder 自动提取第一句做 persona_anchor
3. **对话历史**：一个纯文本数组（最近 N 轮对话）

传进 `ContextBuilder.build("FULL_CHAT", persona=..., messages=...)`，Builder 返回 `{system_content, formatted_messages, recipe_stats}`。

不接记忆库、不接日记、不接哨兵感知——Builder 照跑，那些段静默为空。只显示 A 层（你是谁）+ B 层（现在什么时候）+ E 层（你们刚才聊了什么）。核心人格一致性不依赖任何外部数据源。

## 设计评审摘要

在开源前的架构评审中，我们从生物学（人类记忆系统对照）、社会学（角色一致性理论）、人工智能（LLM 注意力衰减机制）、工程可靠性（降级容错）四个角度审视了这套设计。关键发现：

- **可以定稿的**：分层模型对人类记忆系统的映射是完整的；所有 Recipe 以 persona_anchor 为共同起点保证了跨场景的人格连续性
- **已修复的**：静默失忆的元认知防御（Builder 自我觉察注入）
- **后续优化方向**：引入记忆遗忘权重模型（利用 importance_score/valence 字段加权衰减，替代纯截断）；深夜模式改为渐进式情绪偏移而非二元切换；人格连续性声明（persona_anchor 后追加 50 字符的演化摘要）
