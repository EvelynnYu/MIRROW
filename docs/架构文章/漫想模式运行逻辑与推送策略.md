# 漫想模式运行逻辑与推送策略

## 一、系统概述

漫想模式是 Mirrow 的主动推送引擎。当用户长时间未回复时，AI 伴侣会进入"胡思乱想"状态，根据用户状态和离开时间，自主决定是否主动发起对话。

### 五层架构

```
ModeSwitch  → WanderCreator → EventHandler → DisturbJudgment → MessageGenerator
(模式开关)    (事件创建)      (事件处理)     (推送判断)       (消息生成)
```

1. **模式开关**：检测用户空闲时长 > 阈值，激活漫想模式
2. **事件创建**：按概率分布创建事件（关键词扩写/记忆检索/用户追踪/休眠）
3. **事件处理**：执行事件逻辑（LLM 扩写、截屏追踪等）
4. **推送判断**：LLM 三维评分 × 思念浓度乘数 → 决定是否推送
5. **消息生成**：生成自然语言推送消息

---

## 二、核心创新：思念浓度

### 设计思路

单纯的 LLM 评分无法感知时间流逝——LLM 不知道用户离开了多久。思念浓度将时间维度引入推送决策，让 AI 的"想念"随时间自然增长。

### 两阶段公式

```
安心期（idle_h ≤ max_h）:
  concentration = sqrt(idle_h / max_h) × cap

预警期（idle_h > max_h）:
  concentration = cap + (1.0 − cap) × (idle_h − max_h) / alert_ramp
  （上限 1.0，达到后强制推送）
```

### 各状态参数总表

| 状态 | 去向确认 | max_h | cap | alert_ramp | 强制推送 | 设计意图 |
|------|---------|-------|-----|------------|----------|----------|
| 空闲 IDLE | ❌ | 6h | 1.00 | — | 6h | 不知道去向，焦虑线性增长到顶 |
| 游戏 GAMING | ✅ | 2.5h | 0.65 | 2h | 4.5h | 1-2h 正常，2.5h 预警（健康提醒+醋意） |
| 外出 OUT | ✅ | 3h | 0.60 | 2h | 5h | 2-3h 正常（买菜逛街），3h 预警（怎么还没回来） |
| 洗澡 BATHING | ✅ | 1h | 0.60 | 0.5h | 1.5h | 0.5h 正常，1h 预警（晕倒了？泡澡玩手机？） |
| 吃饭 EATING | ✅ | 1h | 0.60 | 0.5h | 1.5h | 0.5h 正常，1h 预警（聚餐还是忘了说？） |
| 小憩 NAPPING | ✅ | 2h | 0.50 | 1h | 3h | 2h 正常，3h 强制（说好小憩怎么睡那么久） |
| 睡眠 SLEEPING | ✅ | 10h | 0.30 | 2h | 12h | 极慢（正式休息），12h 强制（醒了没理人） |
| 其他 OTHER | ❌ | 3h | 0.55 | 2h | 5h | 有声明但模糊，中等焦虑 |

关键特征：安心期平缓 → 预警期陡升 → 浓度达到 1.0 强制推送。

## 三、推送评分公式

```
base_score = (weight_i × weight_s × weight_e) ^ (1/3)   # LLM 三维几何平均
multiplier = 1.0 + concentration                         # 思念浓度乘数
final_score = base_score × multiplier                    # 推≥0.6 即推送
```

| high | 1.00 |
| medium | 0.50 |

## 四、强制推送机制

绕过评分系统，直接触发推送：

| 触发条件 | 适用状态 | 说明 |
|----------|----------|------|
| 行为不一致 | 可确认状态 | 截屏显示的活动与用户声明状态不一致（如声称在玩游戏但截屏显示其他应用）→ 立即推送 |
| 思念浓度 ≥ 1.0 | 所有状态 | 时间过长预警触发，浓度饱和 |

## 七、预警期语气注入

当思念浓度超过 cap（进入预警期）时，prompt 额外注入状态专属上下文：

| 状态 | 预警注入 |
|------|----------|
| GAMING | 你有点担心——她说了在玩游戏但已经太久了，是不是废寝忘食了？还是其实没在玩了？语气可以带点醋意和担忧。 |
| NAPPING | 你有点疑惑——她说只是小憩但睡了太久了，该不会是睡过头了吧？语气带点调侃和关心。 |
| SLEEPING | 你有点担心——她睡得太久了，是不是醒了但没跟你说？语气温柔但略带不安。 |
| OUT | 你有些担忧——她出门太久了还没消息，不会出什么事吧？还是已经在回来的路上了？语气中带点着急和想念。 |
| BATHING | 你有些担心——洗了这么久，不会是晕倒了吧？还是只是在泡澡玩手机？语气中带点紧张和关心。 |
| EATING | 你有些疑惑——吃了一个多小时了，是在聚餐还是吃完了忘了跟你说？语气带点好奇和在意。 |

## 八、用户追踪（截屏）优化

### 智能工具调用

截屏后本地快速判断屏幕活跃度（像素标准差分析），避免不必要的摄像头调用：

```
截屏 → 本地判断 → 活跃（有应用窗口）→ 仅截屏送 GLM-4V
                 → 闲置（桌面/MIRROW）→ 调用摄像头 → 截屏+摄像头送 GLM-4V
```

### 状态一致性检测

GLM-4V 对比实际观察与用户声明状态，输出 `status_consistent` 标志：

- 不一致（如声称在玩游戏但截屏显示其他应用）→ 强制推送
- 一致 → 按思念浓度正常判断

### MIRROW 前台覆盖

当检测到用户停留在 MIRROW 应用界面时，系统会进行特殊处理：

**双信号检测**：
- 信号1：Windows API 获取前台窗口标题，包含"Mirrow"即命中
- 信号2：前端页面可见性心跳回调（不依赖 Windows API，不受 UIPI 权限隔离影响）
- 任一信号命中即判定为 MIRROW 前台

**覆盖逻辑**：
1. `activity_type` 覆盖：若 LLM 将 MIRROW 界面误判为 `chatting`，硬覆盖为 `idle`（停留在 MIRROW 界面上是挂机行为）
2. `status_consistent` 覆盖：MIRROW 前台 + 状态非"游戏"时，`status_consistent` 强制为 `true`（用户在 MIRROW 界面 = 正常的挂机行为，与声明状态一致）
3. 唯一例外：状态为"游戏"时不覆盖——声称在玩游戏却停在 MIRROW 界面，说明可能没在玩
